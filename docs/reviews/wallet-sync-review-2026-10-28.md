# 同步响应优化 · 0.11.5

## 延迟原因与修改

- 之前先完成三个代币池的历史同步，才开始 NFT。现在两类资产并行；代币 RPC 阻塞不再推迟 NFT 发现。
- NFT 之前从合集部署区块顺序扫描。现在先检查全部已验证合集的最近 128 个确认区块，发现有效持仓后立即加密保存，旧历史随后补齐，生产合集的历史优先于停用测试合集。确认目标仍是 `latest - 1`。
- 最新范围与历史连续游标分别记录。只有补齐中间区间才合并覆盖，不把“已查近期”当作“全部同步完成”。增量检查重用近期游标；重组时验证检查点并撤销孤立记录。
- 历史读取使用现有公开链批量读取 worker，支持 SQD Portal、检查点核对和 RPC 回退。代币池的同范围公开查询可通过 worker 缓存共享；每个池仍单独扫描、解密和推进游标。主网只读验证确认同范围 worker 查询的 `addressCount` 为 3。
- NFT 历史每片最多八页或五秒处理预算，释放 journal 队列后继续。已经发出的网络请求可以超过预算；网络超时后回退，不能跳过未验证页。这样近期检查和发送不必排在整个历史扫描后面。
- 读取生日检查点时先核实哈希，初次补扫可从账户创建范围开始；显式完整重扫仍包含此前历史。
- 藏品页每 15 秒检查近期转入，统一同步期间每两秒读取已保存持仓。扫描保存仍使用同一 NFT mutation queue，避免签名恢复记录被旧扫描覆盖。
- 仅并发核对尚未花费的持仓，保留显式重扫/重组的核对路径。仅查状态时不会广播交易。

## 验证

- 回归包括：代币阻塞时 NFT 仍启动；近期持仓先保存；历史分片断点恢复；生日与完整重扫；近期重组；无新区块不重复读日志；锁定与账户变化；NFT 确认与发送恢复。
- 浏览器覆盖同步未完成时已接收 NFT 的展示、固定字母颜色和现有主页/活动/签名流程。
- 使用全新 Chrome 配置和当前主网公开目录进行只读测量，扫描两个合集最近 128 个确认区块：首次 6,223ms，立即增量检查 1,449ms，第二次没有新的日志请求。这次测量不含真实钱包解密，也不是实际转账到账时间保证；实际时间受 RPC、确认区块和本地解密影响。
- 同一环境验证了现有历史 worker 能读取生产 NFT 合集公共事件页。数据源一次响应可能只覆盖请求范围的一部分，必须按返回的连续覆盖游标继续，不能跳到请求终点。
